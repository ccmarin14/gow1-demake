# Registro de decisiones

Este registro separa las decisiones vigentes del historial del prototipo descartado. El runtime actual es un shell Phaser/Vite neutral; las decisiones de producto siguientes orientan el trabajo futuro y no implican que sus sistemas estén implementados.

## Decisiones vigentes

| ID | Decisión | Motivo |
| --- | --- | --- |
| D-01 | Mantener Phaser 3, TypeScript y Vite como scaffold web 2D. | Es la base ejecutable conservada. |
| D-02 | Diseñar para un lienzo horizontal lógico de 320×180 con presentación pixelada. | **Reemplazada por D-12** para el trabajo futuro; se conserva como registro histórico de la decisión anterior. |
| D-03 | Adaptar la historia del primer *God of War* de PS2 con estética, lectura, estructura lateral y mecánicas estudiadas en *God of War: Betrayal*. | Combina la historia solicitada con el lenguaje de acción lateral sin reutilizar el argumento de *Betrayal*. |
| D-04 | Crear recursos propios y usar referencias externas solo como estudio. | Evita copiar sprites, pantallas, audio o recursos de otros juegos. |
| D-05 | Priorizar herramientas locales y gratuitas; no consumir créditos externos sin autorización explícita. | Mantiene el flujo reproducible y dentro de la autorización acordada. |
| D-06 | Atender una sola tarea activa con orquestador, implementador y auditor distinto; cerrar una tarea documental no autoriza desarrollo y, cuando no haya etapa activa, iniciar desarrollo requiere autorización explícita del usuario. Las etapas de una secuencia de desarrollo ya autorizada continúan automáticamente salvo pausa explícita, bloqueo externo o decisión material pendiente. Antes de corregir un hallazgo de auditoría, el auditor que lo reportó debe aprobar en solo lectura un plan del orquestador con hallazgo/evidencia, archivos exactos, cambio, criterios y regresiones protegidas; si lo rechaza, se revisa el plan sin editar. Tras aprobación, un único implementador corrige y un auditor distinto reaudita; fallos vuelven a la compuerta. | Preserva el control del usuario sobre el inicio de desarrollo y hace revisables las correcciones derivadas de auditoría antes de modificar archivos. |
| D-07 | Mantener como primer objetivo narrativo el Egeo y la Hidra dentro de una campaña que sigue el orden reconocible de GOW1. | Conserva el arco solicitado; el primer tramo no está implementado. |
| D-08 | Priorizar teclado en la primera entrega; reservar `E` para acción contextual y mantenerla separada de `J`/`K` de ataque. | Evita que cofres, mecanismos o prompts contextuales se confundan con ataques. El mapa es propuesto, no está activo. |
| D-09 | Separar simulación, presentación Phaser, entrada, recursos por manifest, UI DOM cuando corresponda y estado serializable. | Evita que los objetos visuales se conviertan en fuente de verdad. |
| D-10 | Diseñar un contrato DEV futuro con snapshots, escenarios, reset, pasos controlados y métricas; distinguirlo de las entradas normales. | Facilita reproducir estados sin confundir una prueba controlada con una partida real. El contrato aún no existe en el shell. |
| D-11 | *(Reemplazada por D-14, 2026-10-15.)* Ejecutar todos los subagentes del proyecto exclusivamente con modelos de la familia Luna; reutilizarlos cuando convenga conservar contexto y crear uno nuevo cuando se necesite independencia, especialidad distinta o el agente esté bloqueado. Nunca ejecutar más de un writer simultáneamente sobre el proyecto. | Se mantienen reutilización de agentes, independencia de la auditoría y un solo writer; se retira la restricción de familia de modelo por no ser verificable en el runtime. |
| D-12 | Para el trabajo visual futuro, usar una resolución interna horizontal de 480×270 y escalar el canvas a una ventana amplia del navegador con pixelado nítido y sin suavizado. | Aumenta el detalle disponible manteniendo una escala de producción manejable; la resolución interna no limita el tamaño CSS del canvas. El shell ejecutable vigente sigue en 320×180 hasta que un cambio de código autorizado lo actualice. |
| D-13 | *(Reemplazada por D-14, 2026-10-15.)* Los subagentes que escriban código trabajan obligatoriamente en OpenCode con modelos Luna; la auditoría de solo lectura puede usar Codex con Luna High y debe ser distinta del implementador. | El requisito de OpenCode/Luna se retira por no ser verificable; se conserva la auditoría distinta y de solo lectura. |
| D-14 | Elegir el modelo de cada subagente según el runtime disponible y la tarea, sin restricción de familia, registrando en el informe qué modelo y runtime usó cada uno; usar el runtime de agentes disponible para los subagentes que implementen código; la auditoría de solo lectura la realiza preferentemente un subagente distinto del implementador; si un subagente o runtime no está disponible, se reasigna o se ejecuta el orquestador dejándolo constancia, sin aprobar su propia tarea; un solo writer a la vez. | Aprobada por el usuario junto con la edición de `AGENTS.md` (2026-10-15): la restricción anterior solo producía bloqueos y no controlaba nada real; lo verificable es la independencia de la auditoría y el orden de escritura. |
| D-15 | Exigir umbrales de game feel en las etapas 6–14: respuesta al input ≤100 ms (≈6 frames), coyote time 60–100 ms y jump buffer ~100 ms en la etapa de salto. | Derivada de PR-01 (`investigacion-y-definicion.md`); Swink fija ≤100 ms para percibir causa-efecto. Aprobada por el usuario 2026-10-15. |
| D-16 | El contrato y harness DEV (etapa 5) incluye trazas de input grabables como formato de reproducción y garantiza paso de simulación fijo desacoplado del render. | Derivada de PR-02; la literatura (arXiv 2402.04938, GDC *Retro City Rampage*) respalda determinismo por traza. Aprobada por el usuario 2026-10-15. |
| D-17 | En oleadas y conducta enemiga (etapas 17 y 20), los enemigos no agresivos mantienen una separación alrededor de Kratos y los agresivos la invaden; la distancia es ajustable por dificultad. | Derivada de PR-03 (GDC 2019, *Evolving God of War's Combat*). Aprobada por el usuario 2026-10-15. |
| D-18 | El guion del Egeo adopta la estructura de escalada del primer nivel de GOW1 (encuentros repetidos de Hidra con repertorio creciente, recompensa a mitad de escenario y clímax en cubierta), sin copiar recursos ni escenas. | Derivada de PR-04. Aprobada por el usuario 2026-10-15; el rango de 57–63 px de Kratos se registra como validación externa (PR-05). |
| D-19 | Añadir tres etapas al plan (26→29): Bloqueo y parry (orden 13), Finisher contextual (orden 18) y Orbes, cofres y mejoras (orden 22). | Resuelve los huecos H-1, H-2 y H-3 detectados en `investigacion-y-definicion.md`; el usuario decidió incorporarlos 2026-10-15. H-4 se resuelve sin cambios: se mantiene Phaser 3 (D-01). |
| D-20 | Adoptar la jugabilidad lateral de *God of War: Betrayal* —incluida su **verticalidad** (ascensos, saltos entre niveles, plataformas y peligros a varias alturas)— como punto de partida a **igualar o superar** en la adaptación web, subordinada a contar la historia de GOW1 y sin copiar recursos (D-04). «Igual o mejor» es una **intención de diseño**, no un criterio medible; su cumplimiento se evalúa con criterios concretos en las etapas de movimiento, salto/plataformas y combate. | El usuario aclaró (2026-10-15) que *Betrayal* es el baseline de jugabilidad a superar en el nuevo alcance web 480×270, no solo una referencia vaga de «estudio». Fija la intención sin prometer una comparación imposible de medir de forma objetiva. |

## Historial descartado

- La implementación de gameplay, arte y audio del prototipo anterior fue descartada el 2026-10-08. Sus controles, balance, enemigos, oleadas y encuentros no forman parte de las decisiones ejecutables actuales.
- El plan numerado de 22 etapas describía el prototipo anterior y no es el plan activo. El plan futuro revisado está en [`docs/verificacion.md`](verificacion.md); por ahora no hay etapa de desarrollo activa.
- La guía visual v1 y sus reglas anteriores se conservan solo como historia; la guía v2 es el criterio de producción visual vigente. Sus muestras retiradas no son un baseline inspeccionable.
- Las aprobaciones previas de etapas corresponden al código descartado. Se preservan como registro histórico y no validan el shell ni una implementación futura.
